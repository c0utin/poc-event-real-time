▣ The load-bearing idea _□✕
ARCHITECTURAL PRINCIPLE

“Applications emit facts about notification lifecycle transitions. Storage and analytical systems decide how those facts are persisted, normalized and queried.”

SERVICES EMIT 
notification.delivery.failed
  error.code = UPSTREAM_TIMEOUT
  attempt    = 2
  retryable  = true
SERVICES NEVER EMIT 
INSERT INTO clickhouse.
  notification_events
  (col, col, col)
  VALUES (...)

The event is the contract. Everything downstream is an implementation detail we are allowed to change.

▣ Medallion — three layers, three different questions _□✕

05Each layer exists because it answers a question the others can't.

BRONZE

“What exactly happened?”

  • Raw event, as emitted
  • Immutable, append-only
  • Schema-tolerant
  • S3 JSON.gz, batched
  • Permanent — the historical record
SILVER

“What does it mean?”

  • One canonical schema
  • v1 / v2 / v3 collapsed into it
  • Deduped on event_id
  • Bad events → quarantine
  • Parquet / Iceberg — open format
GOLD

“What does the product ask?”

  • notification_current_state
  • notification_attempts
  • notification_errors
  • notification_metrics_1m
  • ClickHouse — a projection, not the truth

Preservation, interpretation and query optimisation stay three separate concerns.

Bronze and Silver do not know what OLAP engine exists

▣ ADR-001 — Events are the integration contract _□✕

ADR-001Events are the integration contract

CONTEXT

Notifications are assembled from many services. There is no shared vocabulary for “what just happened”, and no shared place to write it down.

DECISION

Producers emit standardized lifecycle events — notification.enqueue.failed — through a small SDK. Never engine-specific rows.

WHY
  • The event becomes the stable interface between platform and analytics
  • Storage layout, schema and query engine can all change behind it
  • Producers never learn that ClickHouse exists
REVISIT WHEN

Never. This is the load-bearing decision — every other record below is only affordable because the contract is an event.

Status: ACCEPTED — 2026-09-08

▣ ADR-002 — Every operation emits started + terminal _□✕

ADR-002Every operation emits a started and a terminal event

CONTEXT

A worker can die mid-operation. If we only emit outcomes, a crash is indistinguishable from work that never started.

DECISION

Validation, build, enqueue, delivery and callback each emit *.started followed by *.succeeded or *.failed.

WHY

started + no terminal + elapsed > threshold

lets us derive STUCK / UNKNOWN honestly — instead of silently inferring success or failure. Crashes become a queryable state.

TRADE-OFF ACCEPTED

Roughly 2× the event volume. Cheap in S3, and it is the only mechanism that catches the failures nobody reported.

Status: ACCEPTED — 2026-09-08

▣ ADR-003 — No transactional outbox _□✕

ADR-003No transactional outbox

THE PATTERN ASSUMES 
BEGIN;
  INSERT INTO notifications (...);
  INSERT INTO outbox (...);
COMMIT;

… that the entity and the event live in one transactional database.

DECISION

Don't build one. The durable boundary is S3 Bronze: the event is written to permanent storage before anything downstream is trusted.

WHY
  • There is no central notification table to commit against
  • Inventing one purely for analytics would add real state to the hot path and reshape the existing platform
  • We keep the idea that matters — durability before downstream — and drop the mechanism we can't afford
REVISIT WHEN

A transactional notification store appears for product reasons. Then a real outbox is nearly free and worth adding.

Status: ACCEPTED — 2026-09-08

▣ ADR-006 — Normalize before the OLAP engine _□✕

ADR-006Normalize in Silver — before the OLAP engine

CONTEXT

Bronze → ClickHouse directly is simpler, and it works. Materialized views could fold v1 / v2 / v3 events into canonical columns.

DECISION

The canonical model lives in Parquet / Iceberg on S3, defined once, before any engine sees it. ClickHouse loads an already-canonical dataset.

WHY
  • If the transform lives in ClickHouse SQL, ClickHouse becomes the data model
  • Silver is a technology-neutral boundary — Gold is a projection we can drop and rebuild from S3 at any time
  • Engine independence was a stated goal; this is the decision that actually buys it

▣ ADR-007 — Analytics stays off the critical path _□✕

ADR-007Analytics stays outside the delivery path

CONTEXT

Observability infrastructure that can break the system it observes is worse than no observability at all.

DECISION

Event emission is fire-and-forget. No synchronous write, no blocking call, no shared failure domain with delivery.

WHY — WHEN CLICKHOUSE IS DOWN
  • Notifications keep being delivered
  • Bronze keeps accumulating
  • Silver keeps being generated
  • ClickHouse catches up when it returns — or is rebuilt from Silver
THE INVARIANT

analytics failure
≠
notification failure

Status: ACCEPTED — non-negotiable
